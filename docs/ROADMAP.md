# Red Veil delivery roadmap

**Reviewed November 14, 2026.** The latest published game is **[0.4.0-alpha.1](https://github.com/roshaninfordham/NASA-SPACE-APPS-HACKATHON-2026/releases/tag/v0.4.0-alpha.1)**, with nine public assets from exact source `48901d0bce68e72974b36377c3a060f90403ebe9` and signed build `43634324156`, attempt 1. The content-update pack is signed; native app signing/notarization remains separate. [Release notes and changelog](../CHANGELOG.md) identify what players can actually install.

The shipped baseline is one first-person Mars mission plus Mira's five short science lessons and ten questions. The ten outcomes below organize the current delivery work; they are not a claim that the whole game, curriculum, or artistic vision is complete.

## Status meanings

- **Shipped:** available to players in a named public release or verified deployment.
- **Tested:** implemented and checked within the stated scope, but not necessarily published or verified on every platform.
- **In progress:** active implementation, integration, documentation, or assessment remains.
- **Blocked:** a named external dependency prevents the next required step; independent work can continue.

## Six coordinated workstreams

| Workstream              | Outcomes    | Responsibility boundary                                                                                       |
| ----------------------- | ----------- | ------------------------------------------------------------------------------------------------------------- |
| Integration and release | 1, 2, 3, 10 | Integrate accepted changes, verify native behavior, own release claims, serialize Git and publishing.         |
| Browser delivery        | 4, 6        | Browser package/cache/update behavior and browser-specific tests; no claims of native mobile support.         |
| Mobile delivery         | 5, 6        | Android route and iOS/device constraints, signing requirements and physical-device gaps.                      |
| Maintenance audit       | 7           | Trace usage before cleanup, preserve meaningful references and run affected regressions.                      |
| Documentation           | 8           | Keep scope, state, architecture, evidence and team instructions consistent.                                   |
| Media capture           | 9           | Capture the running software, preserve provenance and distinguish provisional presentation from final design. |

File ownership and interface contracts are agreed before parallel edits. Workers hand back evidence; the integration owner performs commits, pushes, and release operations. See [parallel development](PARALLEL-DEVELOPMENT.md). No numerical contribution target overrides these gates.

## Product work beyond this delivery pass

The game still needs more explorable missions and in-world experiments, stronger onboarding/narration, final art and sound, accessibility and controller/mobile refinement, measured performance budgets, and supervised playtests with ages 7–12. The local Bayesian practice estimate is hand-parameterized, not a trained or validated measure of mastery. No cloud learner service is enabled.

Scientific equations, assumptions, units, and NASA observations remain explicit. More realistic visual treatment does not validate every futuristic structure or mission rule. The compressed clock, illustrative hardware/limits, shielding model, and distinct habitat/suit resources require expert review; broader colony systems are not yet simulated. [Core brief](CORE-BRIEF.md), [science](SCIENCE.md), and [learning design](LEARNING-DESIGN.md) remain the governing references.
